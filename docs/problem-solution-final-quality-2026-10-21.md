# Problem Solving: 기록 도구의 완성도와 신뢰성

날짜: 2026-10-21 / 진행: Codex / 상태: 진단·수정·검증 완료

적용 자료: 설치된 `bmad-cis-problem-solving/SKILL.md`, `solving-methods.csv`, `template.md`. 기본 workflow에는 실행 hook이나 추가 제약이 없다. 설정·자료·디자인 관찰의 출처는 Design Thinking 문서에 기록했다.

## 1. Problem definition

표면적 문제는 제너릭한 디자인과 기능적 미완성이다. 구체적인 간극은 ‘실패와 회복의 상태가 코드에는 있으나 사용자 흐름에는 연결되지 않음’이다. 글을 쓴 사람이 그것을 회수하고 의도대로 바꿀 수 있어야 한다.

성공 기준: 크래시·가려진 확인창·거짓 저장 상태 제거, 기기 복구·읽는 문서 내보내기 제공, 클라우드 동시 수정 보호, 모든 주요 화면·상태·키보드·작은 화면 검증, 기존 룰·콘텐츠 유지.

## 2. Boundaries / Five Whys

Is/Is Not: 문제는 기본 룰/카탈로그 35개 테스트가 아니라 React UI·저장 I/O·예외 흐름의 연결에 집중되어 있다. 새 색감이나 장식의 부족이 아니다. 실계정 Firestore 권한은 로컬 검사로 증명할 수 없다.

| 현상 | 직접 원인 | 근본 원인 / 조치 방향 |
| --- | --- | --- |
| 경험 삭제 확인이 가려짐 | 두 Modal이 동시에 렌더되고 뒤의 편집창이 위에 있음 | 개별 boolean마다 독립적인 overlay를 렌더함. 표시 우선순위·초점·배경 잠금을 하나로 수렴 |
| 손상된 시작 초안에서 빈 화면 | 검증 없이 JSON 객체를 spread하고 배열 메서드 호출 | 입력 복구 경계가 게임 상태에만 있고 시작·집필 초안에는 없음 |
| 저장 실패인데 저장 안내 | 저장 오류와 상단 상태가 별개로 관리됨 | I/O 성공 여부 대신 UI 초기 문구를 신뢰. 실제 local/cloud 상태를 구분 |
| 복구본을 쓸 수 없음 | 백업 키만 만들고 복원 UI 없음 | 저장 동작만 구현하고 다시 돌아오는 여정을 검증하지 않음 |
| 체크한 기술이 소실처럼 보임 | checked와 lost가 같은 CSS 규칙을 공유 | 시각적 일관성을 규칙의 의미보다 우선함 |
| 클라우드 덮어쓰기 가능성 | 캐시 snapshot도 초기화로 간주, 무조건 setDoc | 서버 상태 확인과 조건부 쓰기라는 동기화 경계가 없음 |

Five Whys 요약: 사용자가 실패를 회복하지 못하는 이유는 복구 도구가 보이지 않기 때문 → 복구 키만 존재하기 때문 → 정상 저장·기본 진행만 검증했기 때문 → 룰 엔진 테스트 성공을 UI 완성도와 혼동했기 때문 → 기능별 테스트 경계와 전체 여정의 검증이 분리되지 않았기 때문이다.

## 3. Forces and constraints

추진 요인: 명확한 사용자 피드백, 독립된 룰 엔진, 기존 회귀 테스트, 로컬 브라우저 접근. 제약: 사용자 기록 보존, 기존 Firebase 프로젝트 호환, 실계정 로그인 미사용, 불필요한 의존성·리디자인 회피. 주 병목은 시각적 장식이 아니라 안전한 저장과 의미에 맞는 조작이다.

## 4. Solution generation and evaluation

방법: **Failure Mode Analysis**, **Decision Matrix**, **Reverse Brainstorming**(어떻게 글을 잃게 만들 수 있는가를 반대로 뒤집기).

검토한 15개 해법: 검증된 시작 초안, 사건별 집필 초안, 접근 가능한 복구함, 손상 원문 다운로드, 실제 저장 상태, 재연결, 서버 캐시 확인, 조건부 거래, 단일 overlay, 오류 유지, 문서 내보내기, 기록표의 권한 조작, 의미를 보존하는 기술 표시, 책별 일기, 기록형/빠른형 구분.

평가 기준은 글 손실 방지(가중치 4), 핵심 흐름 이해도(3), 기존 정체성·호환성(2), 구현 부담(1)다. 저장 복구·대화상자·상태 의미를 우선 선택했다. 전체 리디자인과 새 프레임워크는 부담은 높고 결함 감소 효과가 낮아 제외했다. 이는 사용자 투표나 정량 사용자 실험의 결과가 아닌 구현 결정을 위한 정성 비교다.

## 5. Implementation / PDCA

Plan: 재현 시나리오와 보존 대상 지정. Do: 저장 경계·UI 흐름을 작은 단위로 수정. Check: 결함별 회귀 및 브라우저에서 확인. Act: 발견된 회귀를 고치고 검증 범위·한계를 갱신한다. 담당은 Codex이며 외부 일정·다른 사람의 작업을 가정하지 않는다.

## 6. Validation and monitoring

테스트 성공과 브라우저 검증을 구분해 기록한다. 실패 원문·이전 기록을 다운로드할 수 있고 현재 기록이 묵시적으로 덮어써지지 않는지가 핵심 판정이다. 클라우드 서버 검증이 없는 동안 상태를 동기화 완료로 표시하지 않는다. 실제 배포 성공은 별도 확인 없이는 주장하지 않는다.

### Do / Check / Act 결과

| 우선순위 | 수정 | 근거·검증 |
| --- | --- | --- |
| P0 | 시작·집필 초안과 게임 파일을 각각 검증하고 읽지 못한 원문을 보관 | `memories:null`, 깨진 JSON, 잘못된 부가 초안, 미래 버전 회귀 검사 |
| P0 | 실제 기기 쓰기 결과로 상태 표시, 게임·시작·집필의 재시도 | QuotaExceededError를 브라우저에 주입해 실패와 재시도를 확인 |
| P0 | 서버 snapshot 확인 후 조건부 거래, 계정별 요청 범위 | 캐시에서 업로드 안 함, 읽기와 쓰기 사이 변경 시 충돌, 계정 전환 중 완료 무시 |
| P1 | 인물·사건별 초안과 접근 가능한 복구함, 손상 원문 다운로드 | 다른 사건 이동·JSON 가져오기 후 이전 글 복원 |
| P1 | 한 대화상자만 표시, 입력·오류·초점 보존 | 삭제 확인 취소/실행, Tab/Shift+Tab/Escape, inert 배경 |
| P1 | 기록표 안의 예외 권한, 올바른 기본 기억 ID, 기술 자체 상실 비용 | 가져온 UUID 기억 용량 변경, 기술 없음의 최후 흐름 |
| P2 | 읽는 내용에 맞는 연대기·책별 일기장, 체크/상실 분리 | 주요 9화면, 긴 콘텐츠, 320–1440px, 빠른 게임 빈 상태 |

반복 중 수정한 회귀: 저장 재시도가 초안 쓰기를 다시 실행하지 않음 → 재시도 신호 연결. 클라우드 저장 실패 후 재연결이 이미 확인한 같은 서버 기록까지 충돌로 판단함 → 같은 계정의 마지막 서버 기준을 유지하고 실제 변경만 충돌시킴. 충돌창의 내보내기가 충돌창에 가려짐 → 보관 대화상자를 우선하고 닫으면 선택 화면으로 복귀. 잘못된 부가 시작 초안이 복원 중 예외를 던질 수 있음 → 상태 변경 전 검증.

42개 테스트, 타입·린트·프로덕션 빌드와 별도 실제 Chrome 조작을 수행했다. 빌드의 Firebase 포함 번들 크기 안내는 남았다. 실제 Google/Firestore 권한·원격 배포는 검증하지 않았다. 모의 전송 결과를 실서버 통합 성공으로 표현하지 않는다.

### Party Mode 최종 감수

설치된 `bmad-party-mode/SKILL.md`와 `customize.toml`을 읽고 resolver로 `code-review-crew`를 선택했다. 해석된 모드는 `session`, memory는 false였다. 독립된 서브에이전트를 실행했다고 주장하지 않는다. 사용자의 자율 완료 지시에 따라 이 코드 감수를 유한한 작업으로 수행했다. 프로젝트 공통 설정이 없어 설치된 resolver와 기본 페르소나를 사용했다.

🎯 **Yui:** “복원할 시작 초안은 화면 상태를 바꾸기 전에 검증해야 합니다.”
🔒 **Vex:** “게임 본문이 정상이더라도 첨부된 `setupDraft`는 잘못된 값일 수 있습니다.”
🌶️ **Boundary:** “인물 생성을 마치기 전에도 내보내기와 재가져오기가 이어져야 합니다.”
😤 **Grumbal:** “충돌창에서 누른 내보내기가 다시 충돌창에 가려지는 경로도 확인해야 합니다.”
🚢 **Dana:** “이 복원 경로까지 확인하고, 실계정 검증의 한계는 보고에 남깁시다.”

이 감수 항목을 코드와 브라우저 검사에 반영했다. 독립 사용자 실험이나 여러 리뷰어의 합의 점수로 해석하지 않는다.
