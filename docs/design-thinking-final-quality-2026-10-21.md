# Design Thinking: 천년의 기록 최종 품질 감수

날짜: 2026-10-21 / 진행: Codex / 상태: 조사·정의·대안 선택·구현·검증 완료

## 실행한 BMAD 자료와 범위

설치된 `bmad`의 `knowledge.py --content`로 core-tools, cis, tea 스킬을 새로 확인했다. 실제 적용한 워크플로는 `/Users/imwul/.agents/skills/bmad-cis-design-thinking/SKILL.md`와 해당 `design-methods.csv`, `template.md`다. 원인 분석은 별도 Problem Solving 문서에 기록한다.

프로젝트의 `_bmad/config.toml`과 공유 실행 스크립트는 없다. 설치된 core-tools의 customization resolver로 두 스킬의 기본 workflow를 읽었고, prepend/append/persistent facts/on_complete 모두 비어 있음을 확인했다. core config 실패 시 중단하지 않는 스킬 지침에 따라 출력 위치는 `docs/`로 정했다. 프로젝트에 BMAD가 설치·설정되었다고 주장하지 않는다. 사용자 지시의 자율 완료에 따라 대화형 체크포인트는 질문 대신 문서 저장과 진행 보고로 수행한다.

## 1. Design Challenge

흡혈귀의 삶을 쓰는 사람은 자신의 글을 잃지 않고, 룰북에 따른 기록표 변화와 다음 사건 진행을 이해할 수 있어야 한다. 검정 제본·밝은 종이·짙은 버건디, Geist/SUIT, 장식 그림 없는 집필 중심 화면을 존중하면서 반복적인 상자·중복 설명·불분명한 상태를 다듬는다.

성공 기준: 손상된 데이터에서 앱이 열림, 저장 실패를 성공으로 알리지 않음, 복구본을 실제로 불러올 수 있음, 한 번에 조작 가능한 대화상자 하나, 키보드로 모든 핵심 조작 가능, 주요 흐름과 반응형 검증 통과.

## 2. EMPATHIZE

사용 자료: 이 대화의 실제 피드백, 이전 감사 기록, 코드, 직접 수행한 브라우저 인지 워크스루. 새로운 사용자 인터뷰·외부 사용성 실험을 했다고 간주하지 않는다.

선택한 방법: **Journey Mapping**, **Empathy Mapping**, 이후 **Role Playing**과 **Assumption Testing**. 인터뷰·장기 Diary Study·Shadowing은 현재 참여자가 없으므로 수행하지 않았다.

| 여정 | 사용자의 일 | 확인한 마찰 |
| --- | --- | --- |
| 시작 | 이름·사람·자원·다섯 경험 작성 | 저장된 시작 초안의 `memories:null`이 앱 전체를 중단시킴 |
| 집필 | 긴 글과 한 문장 경험을 보관 | 초안이 전역 키에 저장되며 백업·이전 초안에 접근할 화면 없음 |
| 특성 변경 | 기술 사용과 상실, 인물·물건 변경 | 체크한 기술에 상실과 같은 취소선, 복구 권한은 이야기 화면 깊숙이 있음 |
| 사건 완료 | 기억·대가 반영 후 다음 사건으로 | 상태와 실패 피드백을 여러 화면·짧은 토스트에 의존 |
| 예외 조작 | 기억 수정·삭제·병합 | 삭제 확인창이 편집창 뒤에 뜸, 가져온 기억 ID와 도구의 기본 ID가 달라짐 |
| 다시 읽기 | 연대기·일기장의 과거 확인 | 기록표와 같은 상자 구조, 책의 이름·기억 소속보다 반복 배지가 앞섬 |
| 보관·복원 | 파일로 보관하고 다시 이어쓰기 | JSON 백업만 있고 읽는 문서 내보내기·기기 복구본 복원 경로 없음 |
| 오류 | 저장 공간·네트워크 문제에서 보호 | 저장 공간 부족 때 상단은 여전히 ‘이 기기에 자동 저장’ |

Empathy map: 사용자는 장식적인 그림·서체·제너릭한 디자인을 거부했고 짙은 빨강과 룰북의 정체성을 원했다. 글쓰기와 규칙 선택에 집중하며 저장·복구의 기계적 세부 사항을 떠맡고 싶지 않다는 요구는 제품 맥락에서의 추론이다. 정체성을 새 취향으로 덮는 리디자인보다 상태의 진실성과 조작의 예측 가능성을 우선한다.

## 3. DEFINE

POV: 긴 시간을 들여 이야기를 쓰는 솔로 플레이어는 현재 기록이 어디에 보관되어 있고 무엇을 바꿀 수 있는지 알아야 한다. 성공처럼 보이는 실패나 보이지 않는 복구본은 글의 손실뿐 아니라 기록 도구에 대한 신뢰를 훼손하기 때문이다.

HMW: 어떻게 실패에서도 글을 회수할 수 있게 할까? 어떻게 룰북의 ‘체크’와 ‘상실’을 시각적으로 구분할까? 어떻게 기록표·연대기·일기장이 각자의 읽기 방식에 맞는 리듬을 가질까? 어떻게 예외 지시를 반복 이동 없이 수행할까?

## 4. IDEATE

선택 방법: **SCAMPER Design**, **Analogous Inspiration**(문서 편집기의 복구함), 작은 **Brainstorming**. 평가 전 검토한 대안은 다음과 같다.

1. 기기 복구함을 노출한다. 2. 손상된 원본을 다운로드한다. 3. 시작 초안을 읽을 때 검증한다. 4. 집필 초안을 사건·인물에 묶는다. 5. 지난 초안을 복구함에 남긴다. 6. 저장 실패 상태를 상단에 유지한다. 7. 클라우드 연결 재시도를 제공한다. 8. 서버 확인 전 업로드를 막는다. 9. 동시 수정은 조건부 쓰기로 충돌시킨다. 10. 대화상자를 한 개만 표시한다. 11. 첫 입력칸으로 초점을 보낸다. 12. 오류를 대화상자 안에 유지한다. 13. 기록표에서 예외 수정 권한을 켠다. 14. 완료한 기록표의 변경 버튼을 비활성화한다. 15. 사용한 기술의 취소선을 없앤다. 16. 일기장 기억을 책별로 묶는다. 17. 연대기를 본문 중심 문서로 만든다. 18. 읽을 수 있는 Markdown을 내보낸다. 19. 빠른 게임에 맞는 빈 상태를 쓴다. 20. 키보드 이동과 긴 문장의 정렬·대비를 보완한다.

보류: 새 테마·서체·일러스트, 애니메이션 추가, 대시보드 재배치, 여러 계정/다인 캠페인 서버, 대규모 상태 라이브러리 도입. 실제 결함을 줄이지 않거나 기존 정체성을 훼손한다.

선택한 세 개의 구현 묶음: **기록의 보관·복구**, **단일 대화상자와 일관된 조작**, **읽는 내용에 맞는 편집적 구성**. 기존 룰 엔진을 유지하고 저장·초안·문서 변환의 작은 순수 함수를 분리한다.

## 5. PROTOTYPE

Role Playing의 실제 코드 프로토타입으로 구현한다. 기준 시나리오는 손상된 초안으로 앱 열기, 경험 삭제의 확인/취소, 여러 사건의 초안 보관, 복구 파일 재가져오기, 빠른 게임 이후 다시 읽기다. 새 시각적 효과 대신 실패 표현·동작 연결·내용별 배치만 변경한다.

## 6. TEST

검증 계획: 순수 저장·초안·변환 함수의 회귀 검사, 기존 룰·카탈로그 테스트, TypeScript/ESLint/프로덕션 빌드, 데스크톱·모바일 Chrome 조작, 키보드·오류·긴 콘텐츠. 클라우드는 별도 테스트 전송 계층으로 충돌·캐시·실패를 검증하고 실계정 검증과 구분한다.

### 실제 구현과 반복

- 저장 경계: `storage.ts`의 시작 초안 검증, 게임 파일 형식·미지원 버전 검사, 원본 복구함을 구현했다. `useWritingDraft.ts`는 인물 고유 ID·사건·방문·대체·시즌별 초안을 저장하며 이전 전역 초안도 이관한다.
- 보관 여정: 교체 전 게임과 현재 초안 백업, 이전 초안 다운로드·현재 사건으로 가져오기, 읽지 못한 원본 다운로드, JSON과 Markdown 보관을 연결했다. 생성 전 시작 초안도 왕복한다.
- 조작: 표시할 대화상자는 한 개로 결정한다. 확인 취소 시 편집으로 돌아오고 배경을 inert로 잠근다. 입력 초점·Tab 순환·Escape·복귀 초점을 확인했다. 실패한 입력과 오류를 유지한다.
- 내용별 편집: 연대기는 본문 중심 단일 문서, 일기장은 책별 소속·이름·용량을 표시한다. 체크 기술은 읽을 수 있는 사용 상태로, 상실만 취소선으로 구분했다. 안내·자리표시자의 대비와 조작 글자 크기를 높였다.
- 정체성 유지: 검정 제본 같은 탐색부, 짙은 버건디, 밝은 종이, Geist/SUIT, 집필/기억 병치, 모바일 기억 접기, 의미 있는 용량 점과 내비게이션 아이콘을 유지했다. 새로운 그림·그라디언트·장식 효과를 추가하지 않았다.

실제 Chrome의 주요 흐름 13묶음, 추가 경계 흐름 8묶음과 9개 화면 × 5개 너비를 실행했다. 저장 실패 재시도에서 초안만 재시도되지 않는 회귀를 발견해 게임·집필·시작 초안 모두 재시도하게 수정했다. 임의의 큰 기억 용량은 점을 대량 생성하는 대신 숫자로 표시한다. 긴 이름은 탐색을 밀어내지 않게 제한하고 전체 이름은 title에 남긴다.

검증은 42개 단위·카탈로그 검사와 실제 Chrome UI 조작, 모의 Firebase 전송을 사용하는 실제 훅 검사로 나누었다. 런타임 오류는 재현 시나리오에서 없었다. 새 사용자 인터뷰나 사용자 만족도 수치는 수집하지 않았다. 현재 결과는 코드·브라우저의 관찰이며 제품의 취향 적합성은 후속 사용자 피드백으로 확인해야 한다. 상세 범위와 한계는 `VERIFICATION.md`에 기록했다.

## 7. Next iteration

다음 체크포인트: 재현한 결함이 사라지는지 먼저 확인하고, 수정으로 새로운 단계를 강요하거나 기존 글·특성을 없애지 않는지 확인한다. 후속 사용자 평가는 실제 사용자 피드백이 도착했을 때 수행하며, 수행하지 않은 인터뷰 점수나 사용성 개선 수치를 만들지 않는다.

최종 성공 기준: 재현한 크래시·가려진 확인창·거짓 저장 안내 제거, 복구 가능한 UI·문서 내보내기 연결, 기존 룰·콘텐츠·저장 호환 회귀 통과. 다음 관찰은 실제 Google 계정과 Firestore 권한, 실제 모바일 Safari·스크린리더, 원격 배포 환경이다. 수행하지 않은 검증을 성공으로 간주하지 않는다.
